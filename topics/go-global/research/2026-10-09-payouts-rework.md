# 提现与结汇精修：研究、核验及退稿记录

日期：2026-10-09。起始提交 `0e4d24e`，同一活动主题 PR #8。

## 写前贡献与检索计划

参照快速入门的具体推导与 `editorial-baseline.md`，本章新增能力应是“判断资金停在哪一段，用真实单据把平台出款与本人入账逐项对上，再提出可回答的问题”。不重做支付平台推荐，不把法规摘录和空表格当作经验分享。

现稿存在三个问题：多张平台表连排、周期与费用重复；未展开任何开发者经历；对账只有单币种算式，读者尚不能处理换汇后实际差额。拟保留全部历史锚点，精修为有证据的资金路径、明确各层限额与申报边界、完整双币种对账及异常询问信。

| 决定 | 需要的证据或产物 | 反证/范围 |
|---|---|---|
| 本人账户能否收、钱何时发出 | Creem/Paddle/Dodo 当前原文，按真实账户核对的问题 | 支持列表不等于具体开户/入账成功，不借用他人身份 |
| 净销售额为何不等于本人到账 | 结算明细原文；逐项分币种演算，保留未解释差额 | 不重复扣税/费用，不将释放时间当作资金丢失 |
| 小额频繁提取还是等待 | 实际适用通道报价及资金需求；固定费用算例 | 不因比例更小就建议长期堆平台余额 |
| 外汇总额、通道限额与申报怎样区分 | SAFE 现行文本、目录、2026 征求意见通知 | 草案不当生效规则，银行路径不泛化到支付机构，软件收入不预先定性 |
| 出款成功却没入账怎么办 | 平台状态定义，归属明确的失败/延迟亲历记录，完整调查材料 | 不能用个案保证某银行或通道可用；无真实交易不伪造单据 |

检索：中文 独立开发 Paddle 到账 提现 手续费 / Creem 支付宝 提现 经历；英文 founder payout delayed reconciliation Paddle Lemon Squeezy first payout。官方逐项复核已引用文档；经验追原文与报告背景，寻找等待、扣费、支持追踪的过程，薄帖只作线索。

## 经验检索、冲突与未采用材料

- 中文检索围绕“Creem 支付宝 提现 经历”“Paddle 到账 提现 手续费”；英文检索 `Paddle first payout bank delayed founder experience`。搜索摘要和 Google 自动总结没有作为证据。
- Yeekal 的个人记录比单纯接入教程多了实际回款叙述，但带推荐利益；标题的快捷承诺与正文早期直达失败是两种不同路径。正文不复制其第三方账户申请、用途填写或“免审核”建议，也没有为中转路径背书。
- 实际阅读 Songxiaoman 的 `https://songxiaoman.com/blog/creem-withdraw-to-alipay/`（2026-03-04）：末尾标“转”，没有完整成功到账结果，主体及原始出处不足；自拟合同模板不能证明真实合同关系。没有登记为正文来源。它提示了应说明“真实协议”和“自己写的业务说明”的区别。
- 前序检索的 HenryZ Paddle 接入文章（2025-04-12）及前端邓浩 Paddle 文章（2022-07-21）没有实际出款结果；小黑丸汇总文章也不足以支持具体到账链，未将其接入/开户主张搬进本章。
- PostNitro 同一案例没有被算成两个独立案例。只取其出款和跨期退款问题解释为什么按结算单重建，不采用作者迁移一周后的满意度推断长期可靠性。
- 当前仍未验证具体大陆银行、本人支付宝档位、支付宝完整报价，以及任何第三方中转账户的完整资格与到账。它们限制路线承诺，不妨碍完成有明确假设的对账方法。正文给出真实业务材料与可回答的问题，未伪造开户、交易或支持答复。

## 独立退稿检查及修订

参照 `quickstart.md` 的连续论述与 `editorial-baseline.md`，检查本章能否完成自己的问题，而非复制入门的获客/验证流程。

1. **原稿把 Creem 银行费称“通用费”**：可能让支付宝读者把不适用的费用写进现金计划。重新读 Payout Accounts 的 Bank Transfer 行后，统一明确银行费适用范围；支付宝完整报价仍留为具体待确认事项。
2. **新稿开篇写“审核未完成”**：原作者只报告因材料审核失败，不能擅自补成某一种流程状态。缩回原文支持的原因，不用推测代替经过。
3. **分流图入口与分支矛盾**：入口原为“尚未入账”，却包含已到账金额不符。改成“这笔回款尚未核对完成”，让三条分支都成立；也把邮件另一结局的假设写清，避免将示例收到款和追踪未到账混在一起。
4. **手机三列表挤，交互结果太远**：来源/待确认表在 390 px 下过长碎行，改为语义化定义列表；结算表压成保留金额的两列，将算式放在表后。互动状态移到控件之后、解释链之前，让选择的后果就近可见。
5. **呈现问题不代替编辑评价**：首次构建混排间距错误已修复；HTML 段落包裹导致 5 处引用未渲染，改用可解析的 Markdown 段落。开发热更新时一次浏览器上下文失效，重新加载后确认真实页面，不加产品 workaround。
6. **静态备用说明意外常显**：`noscript` 前的空行将它分成一个新的 Markdown 段落，嵌套段落被 HTML 解析器移到标签外。保持这一段完整 HTML 块后，启用脚本时不再重复说明，关闭脚本时可读完整算式。查款图的中间分支也进一步收窄为“已经发送，尚未入账”，避免与已入账分支重叠。

最终已复读修订后的完整正文、全部展开日程、图注及两种结局的询问材料。开篇失败经历引出路径条件，跨期经历引出完整结算，再沿同一组金额展开兑换与追踪；没有把个案中转经验转换成可直接采用的账户建议。相对入门新增的能力是从不同净额单据起算得到同一结果，区分未解释差额和未取得汇率，再用具体记录追踪。这一范围内没有遗留的核心推导缺口；仍不证明任何读者已实际收到款，自审也不构成读者认可或整个主题完成。
