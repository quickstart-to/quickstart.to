# 第一轮 beta 的范围与验收安排

状态：准备中，未招募、未开始试读、未升级 `topic.yaml`。2026-10-11，承接全书复审及维护者授权的项目推进。全书已有快速入门 + 26 章，本轮目标是取得可执行性反馈，避免继续以补目录代替验证。

## 限定读者和承诺

邀请具备开发能力、正在考虑或刚开始服务海外用户的中文读者，从各自的实际起点选择任务。主路线限定小型 Web 软件/数字产品；不把原生购买、真实 AI 评估、团队长期交付或商业自托管授权标成已完成实操。地区、语言与身份按读者真实条件核对，不预设人人在美国卖订阅。

“月入 1 万美元”保留为标题目标；正文明确采用当月销售额扣退款、不含代收交易税的讨论口径，利润、到账与个人可支配收入另外核对。验收目标是读者能作出有依据的下一步决定，不以达到收入数字作为读完本书的保证。

## 内容范围与门槛

| 阅读组 | 页面 | 需要取得的结果 | 当前状态 |
|---|---|---|---|
| 第一轮用户与产品验证（核心） | quickstart、validate-idea、market-fit、launch、first-use、retention | 选定可接触的人群，比较原办法，设计有限试用并区分完成、采用和再次需要 | 已有完整草稿与编辑记录；尚无本轮独立试读 |
| 收费与经营（核心） | revenue-models、pricing、payments、payouts、business-review | 说明付款方与交换价值，形成报价，分开交付/退款/到账，计算下一轮工作容量 | Web 订阅本地恢复已补；真实平台联调未完成，不能宣称可直接上线 |
| 实际行为前必读（核心中的条件路线） | compliance、entity、tax、risk | 按真实业务确定需要补的材料与核对事项，不把平台个人准入等同于全部经营许可 | 有带来源的草稿；个案适用不由教学算例替代 |
| 其余 12 个专章 | 基础设施、客服、测量、增长、搜索、邮件、广告、团队、商店、AI/API/插件、权利、资源 | 按实际任务跳读，验证完整产物是否够用 | 深度各异，原生恢复、AI 实测等缺口公开保留 |

上表不是新一轮事实核验的通过表。升为 beta 前，由 fact-check 流程重新核对快速入门及核心路线采用的易变事实，记录每项 claim/source/结果/修改；仅对完整复核的页面更新 `last_verified`。条件路线同样要核验，不能用“仅供参考”免除责任。读者反馈触发的其他专章事实也要随修随核。无错误来源、可解释的判断、可用的产物与技术通过分别验收。

## 一轮可以直接执行的试读任务

先安排 5–8 位读者，每人选 1–2 项任务；这是拟定样本，不是已经有读者。至少覆盖“尚无产品”“已有免费使用”“准备或已开始收费”三种起点，并包含手机阅读。不要要求读者交出真实客户、银行卡、税务或账户资料；可在自己的材料上工作，只提交脱敏结论与卡住的位置。

| 任务 | 给读者的题目 | 可观察的完成结果 | 退回修订的信号 |
|---|---|---|---|
| T1 选路 | 用你当前想法，在本书找到下一项值得验证的问题 | 说出人群、原任务、已有替代及为何先查这一步，并定位到对应段落 | 只会列平台，或把书中虚构案例当真实需求证明 |
| T2 最小试用 | 读选品/首次使用，为一个结果设计有限试用 | 区分输入、输出、独立完成与真实采用；能解释何时暂缓开发 | 只能填空，无法说出哪种结果会改变决定 |
| T3 报价与收入 | 用定价与经营章解释一份报价和一轮收入 | 正确区分单次通行证/订阅，销售额/退款/到账/时间成本 | 把 20 美元乘人数当净利润，或认为必须先做订阅 |
| T4 失败恢复 | 按 S-02 运行或阅读静态时间线，解释补付和旧退款 | 能指出 11 月 4 日补付仍至 12 月 1 日，旧期退款不抹掉本期 | 认为更新卡即付款，或照搬脚本作为生产 Creem 集成 |
| T5 条件义务 | 根据自己的地区与交付方式找到应先查的事项 | 用脱敏材料说明哪一项已知、哪一项需外部答复；不猜准入 | 以 MoR 批准代替主体/税务判断，或在不相关规则里迷路 |
| T6 反馈闭环 | 在一处看不懂的内容上提出带位置的问题，再查看处理结果 | 能提交并找回本人反馈，理解回复/来源/修改的关系 | 丢选区、丢草稿、手机操作不可达，或“已回复”被误作“已修正” |

T6 要等生产反馈功能完成配置与真实验收。工程 PR #9 已有本地合成闭环，默认关闭；它不计为独立读者反馈。首轮可以先收集站内反馈，若功能未开则在维护者现有沟通渠道接收脱敏记录；没有默认授权向任何人发消息或代为招募。

每条记录使用：`读者匿名编号 / 起点 / 设备 / 任务 / 页面与段落 / 原预期 / 实际结果 / 是否需提示 / 严重程度 / 对应反馈 ID / 后续修改 PR / 复测结果`。计时可帮助定位摩擦，不以快慢替代判断是否正确；未回复记未知，不能记为满意。

## 通过与回到修订的决定

- 先修会诱导错误付款、收入判断、数据披露或经营行动的问题，再修无法完成任务的内容和交互。关键问题必须有具体修改和对应复测，不能靠平均满意度覆盖。
- 对每项任务至少取得两份独立执行记录；这是本轮采样安排，不推断总体成功率。失败需要说明是内容、界面、先决条件还是读者任务不在范围内。
- 编辑按 `docs/content-guide.md` §8 复审修订后的核心路线；事实核验、编辑结果和技术结果分开记录。核心门槛未满足就继续 draft；beta 可用之后仍不表示读者将获得真实收入。
- stable 另需一轮真实反馈→来源核验→内容 PR→处理结果回到读者的闭环，以及已运行的到期复核机制。仅有代码、计划和合成测试均不满足。

## 接下来按依赖推进

1. 审阅本内容 PR 与独立工程 PR；修正审阅发现，不直接合并到 main。
2. 对核心路线执行完整事实复核，集中登记高波动规则与未确认项；保持原生/AI/团队等后续专题边界。
3. 反馈功能完成 OAuth、Turnstile、D1 及隐私配置，在实际部署验证登录、提交、导出/删除；邮件只有实际配置并验收后才开放。
4. 维护者提供或自行邀请首轮读者，按 T1–T6 收到记录；本项目不虚构样本或外发邀请。
5. 按一个主题 active PR 处理问题，完成复测后再判断 beta，随后再开展 stable 所需真实维护闭环。
