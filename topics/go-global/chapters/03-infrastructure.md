先搭一套你能恢复、能对账、能解释数据去向的最小系统。验收标准是客户完成注册、付款、使用和退出后，各处状态一致；域名解析成功或首页能打开，只完成了其中一部分。

供应商示例用于说明配置边界，不代表性能、费用或中国大陆个人准入的统一推荐。以下平台与法规资料核验至 2026-10-09。

## 画出请求和数据实际经过哪里

把客户的一次操作按顺序列出：浏览器 → 页面 → 服务端 → 数据库或任务队列 → 第三方 API → 支付和邮件。对每一步记录供应商、地区、保存的数据、失败后的重试方式，以及自己从哪里管理它。

| 部分 | 最小职责 | 验收时需要拿到什么 |
|---|---|---|
| 域名与 DNS | 让客户找到服务，支持邮件认证 | 所有权、到期日、恢复入口、当前解析记录 |
| 页面与服务端 | 展示承诺，授权和执行任务 | 可重现的构建、部署记录、回退版本 |
| 数据与文件 | 保存用户成果和必要交易状态 | 导出、备份、恢复演练结果 |
| 后台任务 | 执行较长工作、处理失败 | 唯一任务 ID、重试和人工补救入口 |
| 邮件 | 登录、收据、重要服务通知 | 发件认证、实际收信、回复处理路径 |
| 支付 | 结账与事件通知 | 订单、事件、权益、退款和出款的关联记录 |

先减少组件数量。新增服务时，要求它解决一个已观察到的问题，并把它收到的数据加入[合规底线](/go-global/compliance)的数据清单。

## 域名所有权和续费要能独立恢复

建议域名账户使用你能长期访问的邮箱，记录注册商、续费方式、域名到期日、DNS 修改权限和账号恢复步骤。不要把所有恢复邮件都依赖于同一个即将过期的域名。

以 Cloudflare Registrar 为例，官方文档写明域名默认加入自动续费。这个默认值不是你的付款方式始终有效、域名必定续费成功的保证；仍应检查实际账户设置和续费结果。[^src-cloudflare-registrar]

保留当前 DNS 配置，在变更托管服务前先准备回退。域名、DNS、应用部署和邮件认证分别验收，避免迁站时只搬了首页却丢失邮件记录。

## 按客户路径测试地区，不凭“海外云”作判断

服务器地区先服从目标客户、依赖服务和数据处理要求，再用实际流程验证。建议至少分别检查目标客户环境与自己的日常开发环境：

- 打开落地页、登录、上传样本并拿到结果。
- 完成支付跳转，关闭页面后重新进入仍能取得权益。
- 收到登录与服务邮件，链接没有过期或跳到错误环境。
- 第三方 API 失败时，看见明确状态，任务不会无限重复消耗资源。
- 维护者能查看告警、回退部署、恢复备份并联系供应商。

记录时间、网络环境、失败步骤和可复现条件。某次访问成功只能证明当次路径；不要把它改写成普遍可用性或性能保证。

## 密钥和环境从第一天分开

支付、邮件、数据库的服务端凭据不要进入浏览器包、公开仓库或截图。以 Cloudflare Workers 为例，官方要求敏感信息使用 secrets 而非明文 `vars`；本地 `.dev.vars` 或 `.env` 文件不要提交 Git，不同环境的 secrets 需要分别配置。[^src-cloudflare-secrets]

建议为开发、测试、生产建立明确的配置表：域名、数据库、支付模式、webhook 地址、发件地址和密钥持有者。用部署时的检查阻止测试收款连接到生产权益库，也阻止生产通知误发给测试用户。

发现密钥泄露时先撤销或轮换，再处理历史记录；仅删除当前文件无法撤销已经泄露的凭据。恢复步骤和账户保护见[风控与账户安全](/go-global/risk)。

## 邮件不是接入 API 就完成

截至核验日，Gmail 对发往个人 Gmail 账号的邮件区分一般发送者与批量发送者：一般发送者至少需要 SPF 或 DKIM，批量发送者需要 SPF、DKIM 和 DMARC；Google 建议发送者配置三者。对营销及订阅邮件，批量发送还涉及一键退订等要求。不要把这一条直接推广为所有邮箱提供商完全相同的规则。[^src-gmail-senders]

建议按实际发件服务配置三项认证，再验收真实收件：登录邮件、收据、退款通知、回复地址及垃圾箱情况。配置通过不等于每封都进收件箱；将发送成功、送达、退信和用户实际完成操作分开记录。

交易通知和推广邮件分别管理。用户关闭营销订阅后，检查推广是否停止；不要因此误停他们获取服务所必需的通知，也不要借交易通知夹带营销内容。

## 备案判断从业务范围开始

本轮读取的《互联网信息服务管理办法》为 2024 年修订文本：适用于在中国境内从事互联网信息服务，区分经营性许可与非经营性备案。2026 年 7 月 3 日网信办发布的另一份文本明确为再次征求意见稿，不能拿草案条款当作已经生效的上线手续。[^src-cn-internet-services][^src-cn-internet-services-draft]

“产品收了钱”“用了海外服务器”“客户说英语”都不足以单独完成个案判断。上线前把经营主体、服务器和网络资源所在地、服务内容、面向地区及分发渠道写成一页，向住所地通信管理部门和接入服务商确认适用许可、备案及材料，保存答复日期。

如果还有 App，工信部通知要求在境内从事互联网信息服务的 APP 主办者履行备案；已有网站备案的，也要补充 APP 信息。不能用网站备案号替代 APP 手续，更不能把这项要求推导为“所有中国开发者的海外App一律相同”。具体分发路线见[应用商店路线](/go-global/app-stores)。[^src-cn-app-filing]

可以带着这段完整描述咨询，而不是只问“我要不要备案”：

> 我以［实际主体］提供［具体功能］，服务器、域名及网络资源为［情况］，向［地区］用户提供［Web/App］服务，按［收费方式］经营，是否涉及许可或备案？需要哪些材料，由谁提交？如果后续增加国内分发或用户上传内容，需如何变更？

## 用恢复演练结束上线准备

从一份备份恢复到隔离环境，验证能打开用户成果并关联订单；回退一次部署，确认旧版本与现有数据兼容；模拟邮件或任务失败，确认有人能收到告警并补救。只展示备份文件存在，不能证明它可恢复。

最后留下一份运维记录：关键账户与恢复方式、供应商依赖、账单提醒、部署与回退、数据导出、告警处理人。记录中只写密钥存放位置，不粘贴密钥本身。

发布材料准备见[冷启动获客](/go-global/launch)，数据流和文案核对见[合规底线](/go-global/compliance)。文末的 Cloudflare、Gmail 和中国官方资料供配置与范围复核时使用。
